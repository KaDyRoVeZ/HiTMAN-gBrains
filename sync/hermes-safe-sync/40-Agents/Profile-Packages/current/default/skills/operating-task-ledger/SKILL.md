# Task Ledger + Hermes Kanban

Task Ledger и Kanban решают разные задачи:

- Task Ledger (`$HOME/.hermes/coordination/task_ledger.py`) — верхнеуровневый журнал поручений пользователя.
- Hermes Kanban (`~/.hermes/kanban.db`) — карточки исполнителей, зависимости, попытки и результаты.

## Порядок

1. До работы создай безопасную запись Task Ledger.
2. Переведи её в `in_progress`, когда работа реально началась.
3. Для межпрофильной работы создай Kanban-карточки с явным `assignee`. В каждой карточке зафиксируй цель, безопасный контекст, критерии готовности, ограничения, ожидаемый формат результата, зависимости и срок только когда он действительно нужен.
4. Свяжи зависимые карточки parent→child. Для нетривиальной работы включай bounded `goal_mode`; одношаговые служебные карточки оставляй one-shot. Не называй bounded-цикл бесконечным.
5. Требуй handoff в формате `Результат / Доказательства и источники / Что осталось`. Заявление исполнителя не является приёмкой: проверь инструментальные вызовы, артефакты и read-back независимо.
6. Не считай назначение исполнителю завершением: `ready`/`running` означает только очередь или работу. На вопрос о текущем состоянии делай один свежий снимок всех незавершённых статусов (`running`, `ready`, `todo`, `review`, `blocked`), программно сверяй итоговое количество и отдельно называй активные задачи, ожидающие зависимостей и реальные блокеры. На автоматическом уведомлении `completed` сначала прочитай полное состояние карточки, проверь заявленные количества по исходному артефакту или независимым readback-пробам и удостоверься, что каждый названный путь существует.
7. Перед созданием follow-up после любого status-уведомления осмотри текущих родителей, детей и зависимости. Продолжай уже существующую ветку; не создавай дубликат задачи или параллельный граф только потому, что старая карточка заблокирована либо завершилась.
8. Если поручение состоит из нескольких этапов, завершай соответствующую запись Task Ledger только после проверки её этапа, но пользователю называй результат промежуточным до закрытия всей цепочки. Укажи, какой уже существующий этап идёт дальше; общий итог обещай только после его проверки.
9. Передай пользователю результат, а не только статус: сначала готовый итог, затем кратко проверку и остаток; укажи точные ключевые числа, Kanban/Task Ledger ID и абсолютный путь или прикреплённый файл. Для незавершённой цепочки не повторяй обещание «сообщу после завершения» вместо фактов: перечисли, что именно осталось. ETA давай только как явно обозначенный диапазон, основанный на свежем состоянии, длительности активных запусков и последовательности зависимостей; если данных недостаточно, скажи, что точной оценки нет. Не заставляй пользователя отдельно спрашивать, где отчёт.
10. Если профильный исполнитель повторно отвечает шаблоном без обязательных реальных tool calls, а владелец просит временно вести текущую цепочку через `default`, сначала осмотри всю активную ветку и переназначь на `default` только ещё не запущенные карточки. Сохрани временный режим в комментарии корневой карточки, а после назначения выполни read-back каждой затронутой карточки; не размножай одинаковый комментарий по всей ветке без необходимости. После auto-decomposition осмотри ветку повторно: новые дочерние карточки могут получить профильных исполнителей уже после первого прохода. Переназначай только карточки без активного run; не прерывай работающие карточки, не создавай дубликаты и не превращай временное решение в постоянное изменение roster.
11. Перед настоящей эскалацией попробуй 2–3 безопасных существенно разных подхода, если это не повышает риск. Если решение владельца всё же необходимо, дай минимум три развёрнутых варианта с действиями, плюсами, минусами и рисками, выдели рекомендацию и добавь четвёртый пустой пункт `Свой вариант`.
12. Заверши Task Ledger с `--result-file` либо заблокируй с короткой причиной.
13. На просьбу закрыть журнал как можно быстрее сначала сверь открытые записи с `tasks.json` и Kanban, затем закрой только подтверждённое, а остаток верни как 3+1. Не рой приватные сессии в поиске названия `owner-only` записи: журнал намеренно скрывает title, и догадка не заменяет артефакт.

## Быстрая зачистка

Разложи каждую незавершённую запись ровно в один класс, затем действуй:

| Класс | Признак | Действие |
|---|---|---|
| Уже сделано | Независимый read-back: нужный контур пуст, родительские Kanban/`completed` уже есть, или живые файлы совпадают с целью | Напиши короткий verification-артефакт и `complete --result-file` |
| Ждёт выбор | `blocked`/`in_progress` с явной причиной выбора, cutover, restart, архитектуры или живой миграции | Не закрывай; включи в 3+1 |
| Зомби | `queued`/`in_progress` без `result_file` и без `reason` | Не дополняй title догадкой и не `complete`; отдельный пункт 3+1 |
| Живая работа | цель ещё не выполнена, даже если смежние записи уже `completed` | Оставь открытой |

- Пустой Kanban доказывай счётчиками статусов: незавершённые — только `running`/`ready`/`todo`/`review`/`blocked`; `done` и `archived` не считай очередью. `kanban_list` без фильтра статуса возвращает и готовое, поэтому не выводи «есть работа» из смешанного списка.
- Запись, заблокированную ожиданием Kanban-цепочки, закрывай только после read-back, что родители и связанные ledger-записи уже `done`/`completed` и файлы результата существуют. Не оставляй блокер «ждёт цепочку», которой уже нет.
- Смежняя `completed` запись не закрывает родительскую живую работу: установка навыка или отчёт preflight не равны внедрению ролей, cutover или restart Gateway.
- Не бери `complete` для записи без файла: CLI требует существующий `--result-file`. Verification-файл должен содержать счётчики, пути и вердикт, а не пересказ сессии.
- После зачистки покажи сначала что закрыто с ID и доказательством, затем сколько осталось, затем 3+1 только по остатку. Не автогигиену зомби и не паузируй живую работу без выбора владельца.

## Команды

```bash
LEDGER="python3 $HOME/.hermes/coordination/task_ledger.py"
$LEDGER add --owner default --domain general --title "Безопасное название"
$LEDGER start T-0001
$LEDGER block T-0001 --reason "Нужны исходные данные"
$LEDGER complete T-0001 --result-file "$HOME/path/to/result.md"
$LEDGER report
```

## Безопасность

- Для личной задачи применяй `--visibility owner-only`: её название не сохраняется в общем JSON/отчёте.
- Не записывай секреты, содержимое почты, персональные документы, платёжные данные и данные скважины.
- Журнал не даёт права отправлять, публиковать, удалять или менять внешние сервисы.
- `completed` допустим только для существующего артефакта.

## Идентификаторы

- Kanban: системный `t_ce7c283e` показывай пользователю как `K-CE7C283E`.
- Task Ledger: `T-0247`.
- Не смешивай эти пространства идентификаторов.
