### Problem

The agent-first operator wave (v0.60.46.0) gave every error, refusal and notice a machine contract
(`code`, `message`, `why`, `fix.next`, `fix.verify`). Five gaps remain where an agent operator still
sees less than a human at a terminal, or where the contract is not yet universal:

1. **Onboarding coaching never reaches an MCP-only agent.** `runInitNudge` (`src/core/onboard/init-nudge.ts:33`)
   and init's first-run decision bundle (`src/commands/init-first-run.ts:96`, `firstRunBundle` `:123`) write
   only through `writeCliNotices` (`src/core/interop-notices.ts:~283`). An agent that talks to gbrain only over
   MCP never learns its brain has stale chunks, thin link/timeline coverage or zero takes, and never sees the
   open first-run decisions (writeback, skills). The post-upgrade notice already reaches the first stdio session
   (`src/mcp/dispatch.ts:905`, `src/core/post-upgrade-notice.ts:53`), so the channel exists.
2. **Every stdio wiring path registers a different MCP surface.**
   - readiness `harness_wiring` fix and init's quickstart: `--surface verbs` (`src/core/readiness.ts:397-398`,
     `src/commands/init-first-run.ts:144`);
   - `gbrain bootstrap hooks` for Claude Code and Codex: `--surface full` (`src/core/bootstrap/hooks.ts:902,919`),
     opencode: `--surface full` (`src/commands/bootstrap.ts:1270-1271`);
   - plugin variants (Claude Code / Codex): `--surface starter` (generated by `scripts/generate-plugin-tree.ts`);
   - OpenClaw plugin manifest: bare `serve` (`openclaw.plugin.json:37`), resolving to config `mcp_surface`, else
     `full`;
   - docs: `docs/protocol/MEMORY_VERBS_v1.md:52-77` say `--surface verbs`.
   The same user gets 7, ~30 or ~130 tools depending on which install command an agent ran. Bootstrap pins
   `full` because its skills need `put_page`/`get_page`/timeline, which `verbs` lacks (`hooks.ts:887-889`).
   **Bug found while grounding:** the F6 hidden-tool hint (`src/mcp/hidden-tool-hint.ts:20`) tells every stdio
   agent "set GBRAIN_SURFACE=full for this machine's gbrain server", but only the plugin launcher
   (`.agents/gbrain-launcher:60`) reads `GBRAIN_SURFACE`; `serve` resolves flag > config > full
   (`src/mcp/surface.ts:172-180`). On a direct registration the advertised fix does nothing.
3. **A losing `serve --http` exits.** stdio serve answers lock contention / missing brain / unreadable config with
   a status-only server exposing one `gbrain_status` tool (`src/commands/serve-status.ts`, `src/mcp/status-mode.ts`).
   `statusModeEligible` excludes `--http` (`serve-status.ts:21-23`), so `cli.ts:2573-2621` rethrows the
   `pglite_busy` connect error and the HTTP daemon exits. A supervisor (launchd/systemd from `mcp expose`)
   crash-loops it; every HTTP client sees a dead endpoint instead of the explanation and fix.
4. **74 suggestion-less `OperationError` sites in 31 files** (`scripts/agent-contract-baselines/
   suggestionless-operation-error.tsv`; list in `suggestionless-hits.txt` beside this plan). Counting rule used
   throughout: 6 of the 74 hits are funnel-helper definitions that serve 108 call sites
   (measured with `grep -c` including each definition line: `shared-skills/adapter.ts` `fail` ×25, `shared-skills/membership.ts` `fail` ×21,
   `commands/sources-lifecycle-args.ts` `invalid` ×25, `company-brain/receipts.ts` `fail` ×23,
   `commands/takes-mutation.ts` `invalid` ×14, `core/embed-facts-options.ts` `invalid` ×6); the other 68 are
   direct sites. Refusals to fix: 68 + 108 = 176, plus 29 in `persistence/administration.ts` [CEO-7] and 1 in
   `commands/eval-gate.ts:464` (and its ~7 `usage(` callers): roughly 210 refusal sites across 33 files. The
   acceptance bar is the scanner, not the count: zero suggestion-less hits and zero `defaulted-suggestion` hits. The TODOS entry names
   `src/cli.ts`; the baseline instead holds `src/mcp/dispatch.ts:854` (the TSV is authoritative).
5. **Consent-gated paid work that is queued carries no consent record, and the approved cap is not enforced.**
   `book-mirror` gets an `Authorization` from `consentGateOrExit` (`src/commands/book-mirror.ts:420`) and
   discards it; its N `subagent` children (`:455`) run in the worker with no `BudgetTracker` scope
   (`src/core/minions/worker.ts:1528`, `src/core/minions/run-child.ts:166` install only submission authority), so
   the printed derived cap (estimate × 1.5) is never applied. **Bug found while grounding:** `enrich --background`
   on Postgres (`src/commands/enrich.ts:950-981`) queues paid `enrich` jobs before its consent gate (`:1022`) runs,
   so a non-TTY agent queues paid work with no authorization at all.

### Goal

Every MCP-only agent on the owner's stdio pipe gets the onboarding coaching and first-run decisions a terminal user
gets, tied to the calls they affect and within the coaching budget and mute rules; every new stdio registration gbrain
writes defaults to one surface (OpenClaw manifest excepted, T5); an HTTP serve that cannot open its brain stays up, explains itself and recovers; the
suggestion-less `OperationError` baseline reaches 0 with each refusal naming its own next step; and every
consent-gated paid command that queues work stores the authorization on each job and the worker enforces the
approved cap.

### Item 1 — Onboarding notices over MCP (stdio)

**Design.**
- New module `src/core/onboard/mcp-onboarding.ts`:
  - `collectOnboardOpportunities(engine, signal)`: the six counts `runInitNudge` runs today, moved out of

    `{ staleChunks, entities, linkCoverage, timelineCoverage, takes, pages, partial }`.
  - A cache with a 6 h TTL (in memory, persisted per brain; see DX amendments), first filled in the background right after the stdio engine boots and
    refreshed in the background when stale (3 s budget with `AbortSignal`, never on a call's critical path), so a
    long-lived serve stops nudging after the user fixes a gap. A call that arrives while the cache is still cold
    gets no onboarding notice; the next affine call does. Test seam `__warmOnboardingCacheForTests`.
  - `onboardOpportunityNotices(counts, cfg)`: one coaching notice per opportunity class, each with its own
    registered, muteable code so the ledger's per-code dedupe (`notice-ledger.ts`, key `session|code`) cannot drop

    `onboard_no_takes` (CLI init keeps `onboard_opportunities`); these four join `NOTICE_CODES` as `coaching`,

    limits) and the read-only fix `gbrain onboard --check` (argv only; `run_onboard` is mutating and admin-scoped,
    so it is never offered as the MCP route). On an MCP transport a CLI-only fix renders `next: tell_user_to_run`
    by the published `deriveNext` table (row 3), so the MCP-only agent relays the command with `user_message`
    instead of trying to run it; each notice carries that `user_message`. The stale-chunk class is suppressed when readiness
    reports embeddings `disabled_by_choice` or no provider (keyless brains: every chunk is unembedded by design).

    `onboard_stale_chunks`, so the two never compete for the 2-per-session budget on one call. Consent stays

- **First-run decisions:** `mcpFirstRunNotices(engine)` reuses `buildInitFirstRunNotices` (`init-first-run.ts:96`)

  open; nothing is persisted on delivery, because delivering an ask is not the user answering it

  the bundle mutes `first_run_decisions` with `mute_notice` (this code joins the muteable set as an explicit

### Item 2 — One surface for every stdio registration gbrain writes

**Design.**

  registration comment names (`put_page`, `get_page`,
  `add_timeline_entry`, `search`, `query` are in `STARTER_OPS`, `surface.ts:89-106`; `get_timeline` is not),

  skill catalogue, which has not been checked against `starter`, and pinning it would narrow every OpenClaw

  the launcher's substitute-or-append semantics (`.agents/gbrain-launcher:13-16`). An invalid value never stops the
  server (that would end it before the handshake, where no agent sees it): it is ignored with a stderr line, and
  the first tool result carries a once-per-process `info` notice `surface_env_invalid` naming the three values
  and the surface actually served. `serve --http` ignores `GBRAIN_SURFACE` and prints one
  stderr line saying so (FOV-6a: an HTTP ceiling never widens without an explicit `--surface` restart;
  `GBRAIN_MCP_FORCE_SURFACE` stays HTTP's narrowing switch).
- **Runtime widening on stdio (CEO dual-voice D1):** `request_tools` (`src/core/ops/request-tools.ts`, already in

  stay the mechanism), then sends `tools/list_changed` (the server already declares `listChanged`,

- **One rule: never narrow an existing install.** A new registration gets `starter`. `bootstrap hooks` keeps a

### Item 3 — Status-only `serve --http`

**Design — one status-only entry point and one re-probe loop for both transports.**
- `serve-status.ts`: `statusModeEligible` admits `--http` (still skipped under `--fail-fast` /
  `GBRAIN_SERVE_FAIL_FAST=1`). `runStatusModeServe(reason, err, args, connect)` stays the single entry point
  cli.ts calls; it branches on `--http` internally. Both cli.ts call sites pass the new throw-only connect (Eng
  amendments); the extraction keeps `cli.ts` at or under its 3199-line ceiling.
- **Shared re-probe:** `status-mode.ts` gains `reprobe(state, connect)`: `probeStatus()` (config + `peekLock()` file
  reads only), then `gatedReconnect` when nothing blocks. stdio calls it from inside a tool call (existing rule:
  at most once per 5 s); HTTP calls the same function from a 5 s background tick [T2] (the daemon has no
  session, and a shared HTTP server is the topology every fix recommends). Every status-only path (both
  transports, the initial classification and each re-probe) goes through these two functions. The `connect` thunk
  is a throw-only connect (Eng amendments; today both status call sites pass bare `connectEngine()`, `cli.ts:2577,2620`,
  which exits on a vanished config or failed repair), so a config removed between probe and connect cannot kill
  the status daemon. A later helper
  that must run on each re-probe (for example engine-identity or migration checks) hooks one place.
- **HTTP status listener** `src/commands/serve-http-status.ts`, started by `runStatusModeServe` for `--http`: a bare
  `node:http` server on the same `--bind`/`--port` with the MCP SDK `Server` + `StreamableHTTPServerTransport` in
  stateless mode (protocol-version negotiation from the SDK) exposing exactly `gbrain_status`:
  - `GET /health` → 503 with the HTTP status payload and `Retry-After: 5`.
  - `POST /mcp` → `initialize` (instructions: transport-aware status line), `tools/list` → `[gbrain_status]`,
    `tools/call gbrain_status` → payload, any other tool → one `serve_status_only` error block.
  - `/.well-known/*`, `/token`, `/authorize`, `/register`, `/admin*` → 503 JSON `serve_status_only` envelope.
  - Unauthenticated by necessity (bearer tokens live in the brain it cannot open). The HTTP payload is built from an
    explicit allowlist, not by redacting the stdio payload: `{ status, reason, why, fix, user_message,
    retry_after_s, contract_version }`, with path-free headline and user-message variants per reason (no brain or
    config path, no PID, no `repair_failed` detail, no `share_http_plan`), fixes rendered for `transport: 'http'`
    (actor `host_admin`, `next: tell_user_to_run`). Every unauthenticated HTTP status response collapses `reason`
    to `unavailable` and the text to "this gbrain server cannot open its brain; its host operator can see why with
    `gbrain doctor`" (Funnel publishes a loopback bind, so the bind address cannot decide); the detailed reason stays
    in the marker file, stderr and doctor.
  - Bind failure: if the port is taken (typically by the HTTP serve that holds the brain), the process exits
    through the existing `listenOrRefuse` refusal (`serve-http-listen.ts:20`: `serve_port_in_use` envelope with the
    next-port fix) instead of entering status mode; two daemons on one port is a configuration error.
  - Discoverability: while running, it writes a per-instance marker `GBRAIN_HOME/serve-http-status-<port>.json`
    (fields in Eng amendments; removed by its own process on recovery and exit). A marker is live when its PID is alive (readiness config plane:
    `process.kill(pid, 0)`, no file access beyond the marker) and, in doctor's probed tier, `/health` answers 503
    within 500 ms; a dead marker is deleted by doctor. Readiness `harness_wiring` and doctor treat a live marker as
    "a shared HTTP server exists but is in status-only mode" (`serve_status_only`, `transport: http`) and give the
    status reason's fix instead of "start `gbrain serve --http`" on a taken port.
- **Recovery:** when `reprobe` connects, the full app is built on the same bound listener and its request handler
  replaces the status handler atomically (Eng amendments); the marker is removed. A lost acquisition race
  returns to status mode with the new reason; a full-server boot that fails after the engine connected (for
  example a migration error) disconnects, releases the lock and returns to status mode with reason
  `brain_unopenable` and a stderr line, instead of exiting. The 5 s tick is injectable for tests.
- **Transport-aware texts:** `statusPayload`, `statusFix`, `statusInstructionLine`, `statusModeErrorResult` and the
  recovered payload take the transport; HTTP text never claims `tools/list_changed` was sent.
- **Stale client lists [X1]:** stateless HTTP cannot push `tools/list_changed` (MCP 2026-07-28 delivers it on a
  `subscriptions/listen` stream to subscribed clients), so a client may call `gbrain_status` on the recovered full
  server. Only a process that entered status mode keeps the alias: `serve-http-mcp.ts` checks it before the
  operation lookup (independent of `surfaceAllowedOps`, which is `undefined` on a full surface with no grants,
  `serve-http-mcp.ts:160`), requires `read` scope, never lists it, and answers `status: recovered` with
  "re-list tools or restart this MCP connection". A server that never degraded answers `unknown_tool` as today.
- **Postgres:** unchanged. A Postgres connect failure on `--http` keeps the degraded-engine path
  (`cli.ts:2622-2649`); status mode applies only to the reasons `preConnectStatusReason`/`statusReasonForError`
  return (no config, unreadable config, PGLite missing/repair-failed/unopenable/lock held).
- **Observability [X2]:** structured stderr lines `serve_status_mode_enter` / `serve_status_mode_recovered`
  (`reason`, `transport`, `elapsed_ms`) on both transports.
- **DX amendments (Phase 2.5):**
  - A human stderr banner in HTTP status mode: the reason, the fix, "re-checking every 5 s; Ctrl-C to stop;
    `--fail-fast` to exit instead".
  - The thin client surfaces the status: `src/core/mcp-client.ts` and `src/core/remote-mcp-probe.ts` read a 503
